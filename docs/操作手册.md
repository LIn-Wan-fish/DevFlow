## 0. 一分钟了解

这是一个**研发协作助手**:你提一个研发问题,它会自己调工具去查 Issue、PR、CI 日志、代码和项目文档,需要综合判断时组织多个 Agent 分工分析,最后给你「结论 + 依据 + 下一步」。**涉及评论、关闭 Issue 这类写操作时,它只出草稿,必须你点确认才会执行。**

| 入口 | 地址 | 用途 |
|---|---|---|
| 工作台 | <http://localhost:3000> | 主界面,日常都用这个 |
| RAG 召回测试 | <http://localhost:3000/rag> | 诊断检索为什么没找到内容 |
| Evals | <http://localhost:3000/evals> | 跑固定评测集,做回归对比 |
| API 文档 | <http://localhost:8000/docs> | 所有接口的交互式文档 |
| 后端健康 | <http://localhost:8000/api/health> | 查看当前跑在哪个模式 |

## 1. 前置条件

**只要求一件事:Docker Desktop 已启动。**

```powershell
docker info --format '{{.ServerVersion}}'
```

能打印出版本号(例如 `29.8.0`)就可以。如果报 `permission denied` 或 `pipe 找不到`,说明 Docker Desktop 没起来 —— **必须先启动它再往下走**。

> **踩坑记录(实测踩过两次)**:
>
> 1. Docker Desktop 如果由**受限进程**拉起,会因为访问不到 WSL 和命名管道而**静默退出**(表现:任务管理器里只剩一个 `Docker Desktop` 进程,`docker info` 报 pipe 找不到)。
> 2. 更隐蔽的一种:**如果它是被某个脚本/终端启动的,那个会话结束时它可能被连带终止**。表现是容器跑得好好的,过一会儿 `docker info` 突然连不上,`wsl -l -v` 显示 `docker-desktop` 变成 `Stopped`。
>
> **建议**:始终从**开始菜单**启动 Docker Desktop,不要用脚本代启。它是常驻 GUI 程序,正常启动后不会随终端关闭而退出。

首次启动需要拉 6 个镜像。本机已缓存,通常十几秒到一分钟。

## 2. 启动 / 停止 / 状态

### 启动

```powershell
cd F:\DSH_Next\DemoFlow
docker compose up -d
```

等大约 15~30 秒,然后打开 <http://localhost:3000>。

启动过程中后端会自动做完三件事,**不需要你手工干预**:

1. 建表(并把 alembic 版本对齐,后续 `alembic` 命令不会冲突)
2. 装载内置研发数据快照
3. 建立 Milvus 向量索引(首次约 5~20 秒;Milvus 起得慢时后端最多等 90 秒)

### 查看状态

```powershell
docker compose ps
```

六个服务应当全部是 `running`:`postgres`、`etcd`、`minio`、`milvus`、`backend`、`frontend`。

### 停止

```powershell
docker compose down          # 停止并删除容器,数据保留
docker compose down -v       # 连数据卷一起删 = 彻底重置(见下)
```

### 彻底重置

改了快照数据、或者数据库被玩乱了想回到初始状态:

```powershell
docker compose down -v
docker compose up -d
```

`-v` 会删掉 PostgreSQL 与 Milvus 的数据卷。下次启动时后端会重新建表、重新装载快照、重新建索引。**你在界面上批准过的记忆、确认过的草稿、跑过的评测记录都会清空。**

### 看日志

```powershell
docker compose logs -f backend      # 后端(最常见)
docker compose logs -f frontend     # 前端
docker compose logs --tail=100 backend
```

## 3. 界面导览

工作台是三栏结构。

### 左栏 · 项目与会话

| 元素 | 作用 |
|---|---|
| `DevFlow AI` 品牌块 | 无交互 |
| `PROJECTS` / `项目` | 分组标题(点「项目」是个显示行,不是按钮) |
| `+ 添加项目` | **演示占位**:点击弹提示。Demo 只内置 `acme/clowder-ai` 一个仓库快照 |
| 仓库节点(如 `clowder-ai`) | 点击切换当前仓库 |
| 展开的会话项 | 点击切换会话。**切换会话会切换对话历史的归属** —— 在「默认会话」里聊的内容,切到「第二个会话测试」就看不到了 |
| `刷新当前项目` | 重新拉取右栏与总览数据 |

> 会话列表目前是内置的两条展示项(`默认会话`、`第二个会话测试`),不是从后端动态读取的。但**切换是真的生效的**:每条会话在数据库里对应一行记录,历史互不串扰。

### 中栏 · 总览 + 对话

**顶部总览条**

| 元素 | 说明 |
|---|---|
| 当前代码仓 | 形如 `acme/clowder-ai` |
| `会话: xxx` | 当前会话名,会作为 `session_id` 传给后端 |
| `Production Workspace` | 环境标识,无交互 |
| `管理项目` | **未接线**,点了没反应 |
| `刷新` | 重新拉取总览与右栏 |

**六个统计卡片** —— 数据全部来自 PostgreSQL 实时查询,不是前端写死的:

`待处理 Issue` · `待 Review PR` · `已处理 Issue` · `已拒绝 Issue` · `失败 CI`(有失败时标红) · `已合并 PR`

**角色选择器**(总览条下方) —— `member` / `viewer` / `maintainer`。用来演示权限闸门:

- `member` / `maintainer`:可以确认写操作草稿
- `viewer`:**无写权限**,确认草稿会被拒(403),并且**越权尝试也会留下审计记录**

**对话区** —— 每条助手回答里嵌着可折叠的「执行轨迹」,这就是这个系统最该看的地方:

```
▾ 执行轨迹  9 个事件
  规划       拆出 4 个任务
             t1 · 梳理关联 Issue 的分类与优先级
             t2 · 评估 PR 改动风险
             t3 · 检查失败 CI 的根因
             synthesis · 汇总工程结论(依赖 t1,t2,t3)
  调用       debug_ci {"number":512}
  结果       debug_ci  CI #512 根因:AssertionError: expected 200 got 401
  证据审查    PR #12 的审查结论是「可合入」,但 CI #512 结论为「失败」…
  引用       docs/api.md > 登录接口 > 响应
```

**快捷指令**(三条固定):点一下就等于把那句话发出去。

**输入框** —— 占位符「输入消息,问问当前代码仓…」。`Enter` 发送,`Shift+Enter` 换行;流式期间输入框禁用并出现「停止」按钮。

### 右栏 · Workspace(五个标签页)

| 标签页 | 内容 |
|---|---|
| `Issue` | 搜索框 + 三个筛选下拉 + 分组计数(未归档/讨论中/待决策/已处理/已拒绝/已关闭)+ Issue 卡片列表,每张卡带「引用到对话」 |
| `PR` | PR 列表,**高风险路径直接标红**(如 `⚠ 高风险 src/auth/login.py`) |
| `CI` | CI 运行列表,失败的标红 |
| `团队` | **静态示例数据**(三个成员的演示条目) |
| `记忆&知识库` | 待批准候选 + 已生效记忆两个区 |

> `Issue` 标签页的「全部时间」下拉**未参与过滤**,只是界面占位;「全部状态」「全部负责人」是真的在过滤。

## 4. 七个常用场景

> **耗时提示**:`LLM_MODE=mock` 时基本都是亚秒级响应;切到真实模型后,单次工具调用约 10~30 秒,一次完整的多 Agent 工作流要 1~3 分钟。轨迹是逐步长出来的,不是卡住。

### 场景 A:CI 为什么挂了

输入(或点第二条快捷指令不适用,直接输入):

```
CI #512 为什么失败?
```

**预期**:轨迹里出现 `调用 debug_ci` → `结果`,回答里带出日志中的原始报错 `AssertionError: expected 200 got 401`,并给出修复步骤。

**看点**:根因是从 CI 日志里**摘出来的原文**,不是模型凭空推测的。

### 场景 B:这个版本能不能发布(多 Agent 协作)

```
检查当前 Issue、PR 和失败 CI,判断这个版本是否可以发布
```

**预期**:轨迹出现完整的 `规划 → 执行中 → 结果 → 证据审查 → 结论`。

**这是最值得看的一条**,因为它演示了整个项目的核心:

1. **Planner 拆任务** —— 拆出「梳理 Issue」「评估 PR」「检查 CI」三个独立任务 + 一个汇总任务
2. **三个专用 Agent 并行执行** —— 不是串行,轨迹里能看到它们交错
3. **Observer 报出冲突** —— `PR #12 的审查结论是「可合入」,但 CI #512 结论为「失败」`
4. **Synthesis 正面回应冲突** —— 结论是**暂缓**,并说明为什么不能只按一方决策

**看点**:如果代码审查通过就合、或看到 CI 挂了就无脑拦,都不需要一个多 Agent 系统。**价值在于两个独立结论打架时,系统把它显式报出来而不是和稀泥。**

### 场景 C:这个 Issue 该分给谁

```
分析 Issue #24 的优先级和复杂度
```

**预期**:返回结构化结果 —— 分类(Bug)、优先级(P0)、复杂度、推荐负责人、行动项、判断依据。

**看点**:优先级来自标签 `priority:P0`,负责人来自 `area:auth` 的负责人映射,**判断依据必须引用 Issue 里的具体信息**,不能是空话。

### 场景 D:写一条评论草稿(安全闸门)

```
给 Issue #3 写一条查询评论草稿
```

**预期**:回答下方出现一张草稿卡片:

```
草稿  comment_on_issue → issue#3          状态:pending
将在 issue#3 下发表评论:这条评论由 DevFlow AI 生成草稿,等待人工确认后再提交。
[确认执行] [拒绝]   确认前不会产生任何副作用
```

**这是最能体现「安全」设计的一条,建议按顺序验证三件事:**

1. **未确认前没有任何副作用** —— 到 `http://localhost:8000/api/drafts/audit` 看,里面**没有** `executed` 记录
2. **点「确认执行」才真的执行** —— 卡片状态变 `executed`;再去看 audit,多了一条 `executed`
3. **越权会被拦下并留痕** —— 把角色切成 `viewer`,再走一遍:点确认会弹出 403 错误;audit 里会多一条 `denied`

第 3 点尤其重要:**被拒绝的尝试同样留痕**。只记录成功的审计等于没有审计。

> 涉及 `close_issue` 这类高风险动作时,确认按钮默认禁用,必须先勾选「我已确认风险」。

### 场景 E:RAG 召回测试

打开 <http://localhost:3000/rag>,输入 `登录接口变更`,点「开始检索」。

**四列的含义**:

| 列 | 含义 |
|---|---|
| 切分 | 进入候选的文档片段(结构感知切分的产物,带标题路径) |
| 向量召回 | 语义近似命中的片段 |
| 关键词召回 | 精确命中标识符的片段 |
| RRF 融合 + 重排 | 最终交给模型的证据 |

**怎么用**:当问答答不上来时,看这四列能定位到底坏在哪一步 ——

- 切分里就没有正确内容 → **切分或索引有问题**
- 切分有、向量召回没有 → **向量通道/Embedding 有问题**
- 向量召回有、融合重排没有 → **RRF 或重排把正确结果挤掉了**

### 场景 F:Eval 回归

打开 <http://localhost:3000/evals>,点「运行评测」。

**预期**:`10/10`,每题下面列出逐条硬规则结果(如 `✓ expected_tool_called`)。页面下方是历史运行表,可以对比多次运行。

**`ragas` 字段的读法**(这里刻意不造假数字):

| 显示 | 含义 |
|---|---|
| `skipped (mock mode)` | mock 模式,没有模型判分,跳过 |
| `unavailable (未安装 ragas)` | 真实模式但没装 ragas 包 |
| 具体指标数值 | 装了 ragas 且跑通了 |

**改了 Prompt、检索配置或工具逻辑之后,复跑同一组题**,对比通过列表的增删 —— 这就是回归。

### 场景 G:记忆沉淀 → 批准 → 召回

这是「长期记忆」的完整闭环,建议走一遍:

1. **沉淀** —— 先问一次 `CI #512 为什么失败?`。跑完后打开右栏「记忆&知识库」标签页,`待批准候选` 里会出现类似
   `CI #512 的失败根因:AssertionError: expected 200 got 401`
2. **验证未批准不生效** —— 此时换一个新会话(左栏点「第二个会话测试」),再问 `再讲讲 CI #512 的失败原因`。看轨迹里的 `上下文` 事件:**记忆命中 0**
3. **批准** —— 回到刚才那条候选,点「批准」。它会移到「已生效」区
4. **验证批准后能召回** —— 再换一个新会话问同一个问题。这次 `上下文` 事件显示:**记忆命中 1**

**看点**:未批准的候选**绝不参与召回**。这道闸门的意义是防止一次错误结论被长期沿用到后续所有会话。

## 5. 模式切换

系统有三个开关,全部通过 `.env` 控制。**改完 `.env` 必须重启 backend 才生效。**

```powershell
# 改完 .env 后
docker compose up -d --force-recreate backend
```

### 5.1 模型:`mock` ↔ 真实模型

| | `LLM_MODE=mock`(默认离线) | `LLM_MODE=openai`(真实模型) |
|---|---|---|
| 响应速度 | 亚秒级 | 单次工具调用 10~30 秒,多 Agent 工作流 1~3 分钟 |
| 花费 | 0 | 按 token 计费 |
| 稳定性 | 完全确定,可复现 | 受网络与模型状态影响 |
| 适用 | 演示、单测、快速走查 | 看真实分析质量 |
| Agent Eval | 10/10 | 10/10 |

**切到真实模型**(以 DeepSeek 为例):

```ini
# .env
LLM_MODE=openai
OPENAI_BASE_URL=https://api.deepseek.com/v1
OPENAI_API_KEY=sk-你的key
OPENAI_MODEL=deepseek-flash
```

```powershell
docker compose up -d --force-recreate backend
```

**切回离线**(推荐日常演示用这个,快且不花钱):

```ini
LLM_MODE=mock
```

**换模型前先确认模型名是上游认的真名** —— 写错了不会在启动时报错,而是第一次调用时抛一个看不懂的 404。查可用模型:

```powershell
docker compose exec -T backend python -c "import httpx,os;from app.config import settings;r=httpx.get(settings.openai_base_url.rstrip('/')+'/models',headers={'Authorization':'Bearer '+settings.openai_api_key},timeout=30);print([m['id'] for m in r.json()['data']])"
```

> **已知兼容性(实测踩过)**:本项目对**思考型模型**(如 `deepseek-flash`)做了专门适配 —— 结构化输出走 `json_mode` 而不是 function calling,工具循环里不伪造 assistant 轮。换成普通模型同样能用,不需要改代码。

### 5.2 研发数据:`snapshot` ↔ `github`

| | `DATA_SOURCE=snapshot`(默认) | `DATA_SOURCE=github` |
|---|---|---|
| 数据来源 | 内置快照,离线可复现 | 真实 GitHub REST API |
| 需要 token | 否 | 是(`GITHUB_TOKEN`) |
| 适用 | 开发、演示、单测 | 接你自己的仓库 |

```ini
# .env —— 两个都必须配,少了任何一个都不会同步
DATA_SOURCE=github
GITHUB_TOKEN=ghp_你的token
GITHUB_REPO=owner/name
```

```powershell
docker compose up -d --force-recreate backend
docker compose logs -f backend      # 看同步结果
```

启动时会:

1. 按 `GITHUB_REPO` 找到或创建仓库记录
2. 同步 Issue / PR(含改动文件与高风险标记)/ CI 运行
3. **对失败的 CI 拉取日志**并落盘 —— 否则 CI 排障只会回「未找到日志」
4. 建立向量索引

**配置不全时的行为(重要)**:token 或 `GITHUB_REPO` 缺任何一个,后端**不装载任何数据**,界面显示空数据并给出提示,日志里有一条 ERROR。它**不会拿快照数据顶替** —— 静默回退会让你把假数据当成真实结论。

> 这条路径用 `httpx.MockTransport` 做了离线测试(分页、限流退避、ETag、日志 ZIP 解压、sync 落库),见 `backend/tests/test_github.py`。真实 token 的端到端同步已实测通过(见下)。

#### 令牌需要哪些权限(实测)

细粒度 PAT 的权限是**逐仓库授予**的,而且**读了不代表能写**。实测矩阵(2026-10-06):

| 想做的事 | 需要的权限 | 实测结果 |
|---|---|---|
| 读 Issue / PR / CI 运行 / 日志 | `Contents: Read`、`Issues: Read`、`Pull requests: Read`、`Actions: Read` | ✅ |
| 本 Demo 同步数据(只读) | 上面这些读权限就够 | ✅ |
| 创建 Issue | `Issues: Write` | ✅ |
| 修改 Issue / 增删标签 / 建标签 | `Issues: Write` | ❌ 同一令牌下 403 |
| 提交文件到分支 | `Contents: Write` | ✅ |
| 提交 `.github/workflows/` 下的文件 | **`Workflows: Write`** | ❌ |
| 开 Pull Request | **`Pull requests: Write`** | ❌ |
| 写仓库 Secret | **`Secrets: Write`** | ❌ |
| 创建仓库 | `Administration: Write` + `Repository creation: Write` | ❌ |

**本 Demo 只需要读权限**就能完整跑通同步。写权限只有在你想让 Agent 真正执行写操作(目前只有 `draft_action`,且需人工确认)时才有意义。

> 有个反直觉的点:**创建** Issue 成功了,但**修改**同一个 Issue 返回 403。所以「能建 Issue」不等于「能管 Issue」,
> 配令牌时别只测创建。

#### 如果本机开着 GitHub 加速器(Steam++ / Watt Toolkit 等)

**症状**:后端日志报 `httpx.ConnectError: All connection attempts failed`,同步一条数据都拿不到。

**原因**(实测):这类工具会把 github 域名写进宿主机 `hosts` 指向 `127.0.0.1`,自己在宿主机监听 443 转发。
但**容器里的 `127.0.0.1` 是容器自己** → 连接被拒。而且它做 TLS 中间人,容器默认 CA 也校验不过。

**解法**(可选叠加,不影响默认部署):

```powershell
pwsh -File scripts/enable-github-accelerator.ps1
```

这个脚本会:① 从 Windows 证书库导出加速器根证书到 `backend/certs/extra-ca/`;
② 用 `docker-compose.accelerator.yml` 重建 backend —— 该文件把 github 域名指向宿主机网关。

> ⚠️ 第 ① 步等于**让容器信任一个本地中间人根证书**。只有在直连 GitHub 不通、又确实需要真实数据时才用。
> `extra-ca/` 目录为空时,合并结果就是纯 certifi,行为与默认完全一致。

排查命令:

```powershell
# 容器把域名解析成了什么
docker compose exec -T backend python -c "import socket; print(socket.gethostbyname('api.github.com'))"
# 正常直连应是 GitHub 的公网 IP;若是 127.0.0.1 就说明被 hosts 劫持
```

### 5.2b 自动周报

对应文章「八大核心能力」里的**自动周报**。右栏 **周报** 标签页可以直接看。

| 项 | 说明 |
|---|---|
| 什么时候生成 | 服务启动时先检查一次,之后默认每 60 分钟检查一次 |
| 幂等 | 按 ISO 周做键(如 `2026-W41`),同一周只会有一份,重复检查不会重复生成 |
| 生成后去哪 | 落库(`weekly_reports`)+ **回写知识库**(`docs/weekly-YYYYMMDD.md`),下一轮索引即可被检索 |
| 手动触发 | 周报页「立即生成」按钮,或 `POST /api/reports/generate?repo_id=1` |
| 配置 | `.env` 里 `WEEKLY_REPORT_ENABLED` / `WEEKLY_REPORT_CHECK_SECONDS` / `WEEKLY_REPORT_DAYS` |

```powershell
# 看周报与调度配置
curl http://localhost:8000/api/reports
```

> **这是一个进程内 asyncio 循环,不是生产级调度器。** 边界已写在 `backend/app/reports/scheduler.py` 顶部:
> 多副本会各自触发(靠唯一约束兜底,不会重复写但会白跑)、进程重启会重置计时(所以启动时先检查一次)、
> 生产应该换成 Celery beat / cron —— 生成逻辑本身在 `service.py`,可以原样搬过去。

### 5.2c MCP 外部工具接入

对应文章第 10 章「MCP 与 Skill 接入:扩展 ChatAgent 的能力」。

| transport | 说明 | 用途 |
|---|---|---|
| `inprocess`(默认) | 进程内直连示例工具(`echo` / `now` / `word_count`) | 离线可跑、单测稳定 |
| `stdio` | **真实 MCP** —— 拉起服务端子进程,官方 SDK 走 JSON-RPC over stdio,先 `initialize` 握手再 `tools/list` / `tools/call` | 演示真实扩展通道 |

```ini
# .env
MCP_TRANSPORT=stdio
MCP_SERVER_ARGS=-m app.mcp.servers.demo_server
```

服务端是 `backend/app/mcp/servers/demo_server.py`(官方 SDK),对外三个工具:
`now`(UTC 时间)、`count_text`(文本统计)、`compare_semver`(语义化版本比较,
判断「能不能发布」时真的用得上 —— 预发布版小于同号正式版)。

**关键**:这些工具会被**注册进工具表**,Agent 真的调得到。可以这样验证:

```powershell
curl http://localhost:8000/api/mcp/tools
# 每个工具都带 "registered": true / false —— 只列得出来但调不到,等于没接
```

单独调试服务端:

```powershell
docker compose exec -T backend python -m app.mcp.servers.demo_server
```

> **一个刻意的取舍**:stdio 模式下**每次调用都新起一个子进程**,而不是维持长连接。
> 生命周期管理在这个 Demo 里是纯粹的复杂度,而工具调用频率很低。
> 代价是每次几十到几百毫秒的启动开销 —— 上生产应换成常驻连接池。
>
> 外部工具一律按**只读**对待:写操作必须走内置的草稿闸门,不能让外部注册的工具绕过人工确认。

### 5.2d Skill 技能扩展

对应文章第 10 章的另一半:「把经验变成可复用方法」。技能是 **YAML 声明**的固定流程,
放在 `backend/app/skills/skills/*.yaml`。

内置 4 个:

| 技能 | 做什么 | 步骤 |
|---|---|---|
| `repo_health_report` | 拉仓库健康数据 + 生成周报摘要,用于周会同步 | `repo_health` → `weekly_report` |
| `ci_failure_triage` | 对失败的 CI 做根因排障 + 检索相关代码 | `debug_ci` → `search_code` |
| `issue_intake` | 新 Issue 分诊 + 检索可能相关的文档 | `analyze_issue` → `search_docs` |
| `release_readiness` | 发布前多 Agent 判断 + 仓库健康 | `run_workflow` → `repo_health` |

```powershell
# 列出技能(带 registered 字段)
curl http://localhost:8000/api/skills
# 按技能名执行
curl -X POST http://localhost:8000/api/skills/ci_failure_triage/run -H "Content-Type: application/json" -d "{\"inputs\":{\"repo_id\":1,\"number\":512,\"query\":\"login\"}}"
```

**关键**:技能会被注册成 Agent 工具(`skill__<name>`),Agent 真的调得到 ——
`/api/skills` 里每个技能都带 `registered: true/false`。章节 10.2 的标题就是
「MCP 与 Skill **怎么进入 ChatAgent**」,只列得出来但调不到等于没接。

> **`repo_id` 不暴露给模型**:它就在运行上下文里,从模型可见的参数表里摘掉了,
> 由桥接层自动补入。让模型去猜仓库 ID 只会多一类填错的可能。
>
> **含写操作的技能会被标成 `is_write=True`**:技能步骤里若出现 `draft_action`,
> 整条技能就要过同一道安全闸门。包一层封装不能成为绕过人工确认的后门。

### 5.2e 界面:可拖动面板与深浅色

**拖动分栏**:鼠标移到左栏右侧或右栏左侧的**分割线**上,光标会变成 `col-resize`,按住拖动即可。

| 操作 | 效果 |
|---|---|
| 拖动分割线 | 调整宽度,范围已做夹取(左 180~420,右 280~640) |
| **双击**分割线 | 复位到默认宽度 |

**深浅色**:左栏左下角的 ☾ / ☀ 按钮切换。

所以做法是**把这些语义色指向 CSS 变量**,明暗两套值定义在 `globals.css` 里。
组件只写 `bg-panel text-ink`,**不需要写任何 `dark:` 前缀** —— 换肤只改一处,不用翻几十个组件。

状态色(原先散着 `bg-amber-50` / `text-red-600` 这类写法,共 51 处)也一并收敛成
`bg-warn-soft` / `text-danger` 这样的语义名:调色板颜色在深色底上会变成刺眼的白斑。

### 5.3 角色与认证

在工作台总览条下方切换角色,只影响写操作权限:

| 角色 | 权限 |
|---|---|
| `viewer` | 只读。确认写操作草稿会被拒(403)并留审计 |
| `member` | 可确认写操作草稿 |
| `maintainer` | 同 member(Demo 里未区分更细的权限) |

**角色由服务端从请求头解析,不接受请求体或查询参数**。也就是说
`{"role": "maintainer"}` 或 `?role=maintainer` **都不会提权** ——
`viewer` 照样被拒。这一条有测试守着(`test_请求体里的_role_不参与授权`)。

#### 演示模式 vs 令牌模式

| | 演示模式(默认) | 令牌模式 |
|---|---|---|
| 触发条件 | `DEVFLOW_ROLE_TOKENS` 留空 | 配置了 `DEVFLOW_ROLE_TOKENS` |
| 角色怎么来 | 请求头 `X-DevFlow-Role`,默认 `viewer` | 令牌映射,服务端决定 |
| 是否认证 | **否** —— 客户端仍可自称角色 | 是(简单共享令牌) |
| 界面提示 | 黄色告警条明示「不构成认证」 | 显示「已启用角色令牌认证」 |

`GET /api/auth/mode` 会如实报告当前状态(`enforced: true/false`),前端据此显示提示 ——
**没有认证这件事必须写在脸上**,不能让人以为有权限体系。

开启令牌模式:

```ini
# .env
DEVFLOW_ROLE_TOKENS=viewer:tok-viewer,member:tok-member,maintainer:tok-maintainer
```

```powershell
docker compose up -d --force-recreate backend
```

之后请求必须带 `Authorization: Bearer tok-member`(或 `X-DevFlow-Role-Token: tok-member`),
缺失或不匹配一律 401。工作台的演示界面**不会**自动带令牌,开启后需自行调用 API。

> 注意:这是**最小可用**的认证,不是生产方案 —— 没有用户体系、没有令牌轮换、没有 HTTPS 强制。

## 7. 故障排查

| 现象 | 原因 | 处理 |
|---|---|---|
| 后端日志报 `httpx.ConnectError` | 本机 GitHub 加速器把域名指向了 127.0.0.1,容器解析到自己 | 跑 `scripts/enable-github-accelerator.ps1`(见 5.2) |
| `integer out of range` 且来源是 `ci_runs` | 早期版本 CI 编号用了 `INTEGER`,装不下 GitHub 的 64 位 run id | 已修(`BigInteger` + 迁移 `840c5c18b5dc`);旧库执行 `alembic upgrade head` |
| `docker info` 报 `permission denied` | Docker Desktop 没启动 | 从开始菜单启动 Docker Desktop,等托盘图标变绿 |
| 页面打不开 / 连接被拒 | 容器没起来 | `docker compose ps` 看状态;`docker compose logs --tail=50 frontend` |
| 页面打开了但数据全 0 / 报「加载失败」 | 后端没起来或数据库没装载 | `curl http://localhost:8000/api/health`;`docker compose logs --tail=50 backend` |
| 对话报「上游模型暂时不可用」 | API key 错、余额不足、或网络不通 | 检查 `.env` 的 `OPENAI_BASE_URL` / `OPENAI_API_KEY` / `OPENAI_MODEL`;切回 `LLM_MODE=mock` 先确认功能本身正常 |
| 启动时报 `LLM_MODE=openai 缺少必填项` | `.env` 里三项没配齐 | 补全 `OPENAI_BASE_URL` / `OPENAI_API_KEY` / `OPENAI_MODEL` |
| RAG 检索一直为空 | Milvus 还没就绪,首次索引被跳过 | `docker compose logs backend \| Select-String 索引`;手工重建:`docker compose exec -T backend python -m app.rag.indexer --repo 1` |
| 检索不到刚写进知识库的周报 | 新增文档需要重新索引 | 同上,手工重建索引 |
| 多 Agent 工作流很慢/像卡住 | 真实模型跑完整工作流要 1~3 分钟 | 看轨迹是否在逐步新增事件;要快就切 `LLM_MODE=mock` |
| 端口被占用(`8000` / `3000` / `5432`) | 本机已有服务占用 | 改 `docker-compose.yml` 里的端口映射,例如 `"18000:8000"`,同时把 `.env` 里的 `NEXT_PUBLIC_API_BASE` 改成新端口 |
| `alembic upgrade head` 报「表已存在」 | 老版本遗留问题 | 现已修复(应用建表后会把 alembic 版本对齐到 head)。若仍遇到:`docker compose exec -T backend alembic stamp head` |
| 单测很慢或报网络错误 | 单测被 `.env` 的 openai 模式带跑了 | 已修复:测试夹具强制 mock,单测永不联网。若你另写了测试,注意不要绕过 conftest |

## 附:页面打不开 / API 文档空白怎么办

这两类问题**服务端测试全都发现不了**,排查时容易白费功夫,所以单独写清楚。

### 1. 工作台 / RAG / Evals 页面没有数据

前端(`localhost:3000`)和后端(`localhost:8000`)是**不同源**的,
浏览器会拦掉所有没带 CORS 头的响应 —— 表现就是页面一直"没有数据",
并显示一条橙色提示(里面会提到"快照")。

**根因曾是:后端根本没配 CORS。** 服务端的 httpx 测试不带 `Origin`,
所以一直是绿的 —— 这个 bug 能活很久正是因为测试方式不对。

自查:

```powershell
# 预检必须返回 200 且带 access-control-allow-origin
curl -i -X OPTIONS http://localhost:8000/api/repos `
  -H "Origin: http://localhost:3000" `
  -H "Access-Control-Request-Method: GET"
```

允许的来源在 `.env` 里配置:

```ini
CORS_ORIGINS=http://localhost:3000,http://127.0.0.1:3000
```

> 如果你不是用 `localhost` 访问(比如用局域网 IP `192.168.x.x:3000`),
> 必须把那个地址也加进去 —— **不能用 `*`**:一旦 `allow_credentials=True`,
> 浏览器会直接拒绝通配符来源。

### 2. `http://localhost:8000/docs` 一片空白

FastAPI 默认的文档页从 `cdn.jsdelivr.net` 加载 Swagger 的 JS/CSS。
国内网络下这个 CDN 经常连不上或极慢,页面就是空白 —— 而服务端一切正常。

**已改成后端自己托管**:静态资源放在 `backend/app/static/swagger/`,
随仓库一起分发,**不依赖任何外网 CDN**。`/redoc` 同样处理。

顺带一个坑:FastAPI 默认 HTML 会引用 `SwaggerUIBundle.SwaggerUIStandalonePreset`,
而那个 preset 其实在**另一个文件**(`swagger-ui-standalone-preset.js`)里 ——
只替换 js 地址而不加载它是**直接白屏**。所以 `/docs` 的 HTML 是自己写的,
显式加载两个脚本把它接上。

### 3. API 文档是全英文 / 分组看不懂

`/docs` 上显示的东西有三层,默认都可能是英文:

| 层 | 默认行为 | 现在 |
|---|---|---|
| 应用说明 | 空 | 中文,含能力清单与三种模式对照表 |
| 分组名 | `APIRouter(tags=["repos"])` 里的英文标识 | 中文(仓库 / Issue 分诊 / PR 审查…) |
| 接口标题(summary) | **从英文函数名自动生成**(`List Repos`、`Run Skill`) | 中文 |
| 参数说明 | 无 | 中文 |

文案集中在 `backend/app/api/descriptions.py`(分组说明与应用说明),
接口的 `summary` 与参数说明写在各自路由上 —— **和代码放在一起**,
改了接口顺手就能改文案。`TAGS_METADATA` 的**顺序就是页面上分组的顺序**,
按「先看仓库 → 再看具体工作 → 最后是扩展与权限」排,不是字母序。

新增接口时如果忘了写 `summary`,`tests/test_web.py` 会直接失败 ——
它逐个检查每个接口的 summary 是否含中文。

### 验收里对应的回归测试

`backend/tests/test_web.py`(8 条):跨域预检、实际响应的 CORS 头、
写接口的预检、未知来源不被放行、文档页不含任何外部 CDN、
standalone preset 被加载、静态资源可访问、ReDoc 同样不依赖 CDN。
