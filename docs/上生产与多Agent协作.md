# 从 Demo 到线上:多 Agent 协作与生产化路线

> 这份文档回答两个问题:①怎么把当前这套「多 Agent 编排」做成**真正的多 Agent 协作**;
> ②怎么从**本机 docker compose** 走到**真正线上跑**。
>
> 写的时候尽量贴着当前代码的实际状态 —— 每一条差距都指到具体文件和行,
> 而不是泛泛而谈「要加监控、要加限流」。

---

## 第一部分:当前的多 Agent 到什么程度了

### 已经做到的

`app/agents/orchestrator.py` 里的 `run_workflow` 是一条 **LangGraph 状态图**:

```
planner(拆解) → dispatch(并发执行专用 Agent) → observer(找冲突) → synthesis(综合)
```

- **专用 Agent 有明确职责边界**:`repo_health` / `issue_triage` / `pr_review` / `ci_debug` / `safety`
- **并发执行**:多个子任务用 `asyncio.gather` 并行
- **交叉检查**:observer 会指出「PR 说可合入、但 CI 是失败的」这类**结论冲突**
- **结论可追溯**:每一步都落 `AgentRun` / `TaskRun` / `WorkflowRun` / `ToolCall`

这是一个**编排式(orchestrated)多 Agent**系统 —— 和「一个 Agent 顺序调工具」相比已经是质的区别。

### 还差什么才算「真正的协作」

| # | 差距 | 现状 | 要做成什么 |
|---|---|---|---|
| 1 | **一次性派发,不能重规划** | planner 一次拆完就执行到底 | 根据执行结果**决定要不要再派**新任务(带最大轮次上限) |
| 2 | **Agent 之间不直接通信** | 各自把结果交回 synthesis | 共享黑板 / 消息总线,Agent B 能看到 Agent A 的中间结论并**质疑**它 |
| 3 | **所有 Agent 同一个模型** | 都用 `OPENAI_MODEL` | 按角色分模型:分诊用便宜的,综合用强的 |
| 4 | **工具没有按 Agent 隔离** | 所有 Agent 共享同一张工具表 | 每个 Agent 只能拿到职责范围内的工具(安全之外还有**成本与稳定性**意义) |
| 5 | **没有预算与终止条件** | 靠步数上限 | token / 金额 / 墙钟时间三重预算,超了要**优雅降级并说明** |
| 6 | **没有人在回路的中断点** | 只有事后草稿确认 | 关键决策点暂停等确认(Graph 的 `interrupt`) |
| 7 | **状态只在内存里** | 图状态随请求结束消失 | checkpointer 持久化,**支持断点续跑** |

### 落地路径(建议顺序)

**第 1 步:给图加 checkpointer**(收益最大、改动最小)
LangGraph 支持把状态存进 Postgres。做完之后:长任务可以断点续跑,
前端刷新不会丢,也为第 6 步的 `interrupt` 打底。

**第 2 步:把「一次性派发」改成「可重规划」**
给 planner 的输出加一个「是否还需要补充调查」的判断,
配合最大轮次上限(建议 3)与预算检查。

**第 3 步:Agent 间共享工作区**
最小实现:给 `WorkflowRun` 挂一张 `agent_messages` 表,
每个 Agent 完成时写一条结构化发现(结论 + 依据 + 置信度),
后续 Agent 读全部已有发现。这一步是「协作」和「并行」的分水岭。

**第 4 步:按角色分模型 + 工具白名单**
`config.py` 里加 `AGENT_MODEL_<ROLE>` 与 `AGENT_TOOLS_<ROLE>`,
在 dispatch 时按角色过滤工具表。

**第 5 步:预算与终止**
在 `AgentOutcome` 已经统计 `total_tokens` 的基础上,加金额估算与墙钟上限,
超预算时返回**明确说明**(而不是静默截断)。

**第 6 步:人在回路**
用 LangGraph 的 `interrupt` 在「准备执行写操作」处暂停,前端做确认后续跑。

> **顺序建议的理由**:1 和 3 是地基,做完之后 2/4/5/6 都是在这个地基上加东西。
> 反过来先做 6(暂停/续跑)而没有 checkpointer,就得自己造一套状态持久化。

## 第二部分:当前离「线上跑」差什么

### 先说结论:现在**不能**直接多副本部署

不是因为代码写得不好,而是有几处**进程内状态**。多开一个副本就会出错或做重复功:

| 位置 | 问题 | 影响 |
|---|---|---|
| `app/github/client.py:46` `_ETAG_CACHE` | 进程级字典 | ETag 缓存命中率下降(不致命,但白花钱) |
| `app/reports/scheduler.py:56` 循环 | **每个副本都会跑** | 靠 `(repo_id, period_key)` 唯一约束兜底不会重复写,但会**白跑**并重复调模型 |
| `app/api/chat.py:69` `asyncio.Queue` | 单请求内有效 | 单次对话没问题;但**断线重连无法续看**,也没有跨实例的轨迹推送 |
| `app/tools/registry.py:70` `REGISTRY` | 启动时构建 | 无害(MCP/Skill 发现是确定性的) |

### 生产化清单

#### A. 必须先改的(否则跑不起来 / 会出错)

1. **前端不要用 `next dev`**
   现在 `docker-compose.yml` 里是 `command: ["npm","run","dev"]`。
   生产必须 `next build` + `next start`(dev 模式慢一个数量级,且会按需编译、内存持续增长)。

2. **调度器改成单例**
   把 `app/reports/scheduler.py` 从「进程内循环」挪成**独立的一次性任务**
   (K8s CronJob / 云平台定时任务 / Celery beat),或者用 Redis 分布式锁选主。
   生成逻辑本身在 `service.py`,可以原样搬 —— 这一点当初就是按「可搬走」设计的。

3. **ETag 缓存挪到 Redis**
   `_ETAG_CACHE` 换成 Redis;顺带解决多副本下的缓存一致性。

4. **数据库迁移进部署流程**
   现在靠 `_ensure_schema()` 兜底。生产要用 `alembic upgrade head` 作为**部署步骤**,
   并且迁移必须**向后兼容**(先加列、再切流量、最后删旧列)。

5. **密钥不进 `.env` 文件**
   用平台的 secret 管理(K8s Secret / AWS Secrets Manager / Vault)。
   当前 `.env` 已 gitignore,但文件形式在多机部署下不可行。

#### B. 上线前应该有的

6. **认证换成 GitHub App**
   现在用 PAT(`GITHUB_TOKEN`)+ 共享角色令牌(`DEVFLOW_ROLE_TOKENS`)。
   - GitHub App:装到组织上,权限细粒度、令牌自动轮换、不绑个人账号
   - 用户身份:接 OIDC(如 GitHub OAuth),而不是共享令牌 ——
     **审计日志里记的应该是真实的人**,否则"谁批准了这次写操作"这栏没有意义

7. **长任务队列化**
   SSE 适合「几分钟内出结果」。如果工作流要跑十几分钟,
   应该改成「提交任务 → 返回 task_id → 前端轮询/订阅进度」,
   任务本身丢给 worker(Celery / Arq / Temporal)。**好处还包括重试与幂等**。

8. **可观测**
   - 结构化日志(现在主要是文本日志)
   - OpenTelemetry 链路:一次对话串起 LLM 调用、工具调用、GitHub API
   - 指标:每租户 token 消耗、各 Agent 耗时分布、失败率、GitHub 速率限制余量
   - 告警:预算超支、错误率、CI 失败堆积

9. **限流与配额**
   现在没有。至少要:每用户/每仓库的请求限流、**每租户的模型 token 预算**、
   GitHub API 速率限制的自我保护(现在靠 `conclusions.py` 之类的逻辑正确性,但没有退避)。

10. **优雅关闭**
    `--workers N` 时 uvicorn 需要正确的优雅关闭;SSE 长连接要能被主动断开并让客户端重连。

#### C. 安全与运维

11. **容器安全**:非 root 用户、只读根文件系统、最小基础镜像、依赖漏洞扫描
12. **网络策略**:后端与 Milvus/MinIO 之间不应暴露公网;MinIO 默认凭据必须换
13. **审计留存**:现在审计落在同一张业务库。生产建议**单独存储 + 不可篡改**(追加写、定期归档)
14. **数据保留策略**:会话、运行轨迹、记忆条目都要有 TTL
15. **成本控制**:模型调用的**缓存**(相同问题不重复烧钱)、按预算熔断

#### D. 部署与发布

16. **镜像构建与推送**:CI 里加 build → push 到 registry(现在是 CI 只跑测试)
17. **环境分离**:dev / staging / prod 三套配置,staging 用真实但隔离的仓库
18. **发布策略**:滚动/蓝绿;数据库迁移与代码发布的顺序
19. **回滚**:镜像版本可回退;**迁移要能回退**(或在发布说明里明确不可回退点)
20. **冒烟测试**:发布后自动跑一遍 `scripts/verify_api.py` 的核心几条

## 一个务实的建议:分三步走

**第一步:先让它「能被别人用」(1~2 周)**
前端切 `next build`、迁移进部署流程、密钥进平台 secret、接 OIDC、
调度器挪成独立任务。做完之后可以部署到一台公网机器给团队用。

**第二步:再让它「扛得住」(2~4 周)**
ETag 缓存进 Redis、长任务队列化、限流与配额、可观测三件套、
优雅关闭与健康检查。做完之后可以多副本。

**第三步:最后才是「多 Agent 协作升级」**
checkpointer → 共享工作区 → 可重规划 → 按角色分模型 → 预算 → 人在回路。
这一步和前面两步**可以并行**:它主要改 `orchestrator.py` 及其周边,
不依赖部署形态。

> **为什么不建议反过来先做多 Agent**:多 Agent 更复杂之后,**调试成本会急剧上升**。
> 而没有可观测、没有 checkpointer 的多 Agent,出了问题基本只能靠日志猜。
> 先把「看得见、跑得稳」建起来,再往上加智能,顺序反过来会很痛苦。

## 附:哪些已经做对了(不用改)

- **依赖隔离**:ragas 单独一个容器(它和主程序 langchain 版本冲突,混在一起主程序起不来)
- **模式开关**:`LLM_MODE` / `EMBED_MODE` / `DATA_SOURCE` 三个独立开关,
  离线可跑、真实可用,互不混用 —— 这让本地开发和生产可以共用一套代码
- **写操作闸门**:草稿 → 人工确认 → 审计,这条链路是**服务端强制**的,
  不依赖前端配合;外部注册的工具(MCP/Skill)也统一按只读对待
- **诚实性**:检索不到就说检索不到、评测算不出来就说明原因,不用假数据顶替 ——
  这一点在生产环境尤其重要,因为没人会去核对每个数字
- **周报生成逻辑与服务分离**:`service.py` 可直接搬到任何调度器上
